# Подключение «Ялты» к iiko

Проверено по официальной документации iiko 7 ноября 2026 года. Эта инструкция описывает следующий этап разработки. В текущей версии сайта используются демонстрационные блюда и локальные данные браузера: настоящие заказы, SMS, платежи, бонусы и бронирования в iiko пока не отправляются.

## Что нужно подготовить владельцу ресторана

1. Доступ администратора к iikoWeb тестового предприятия и название организации, из которой будем брать блюда.
2. Приложение на [портале разработчика iiko](https://api.iiko.help/quickstart): `appId` и `clientSecret`.
3. API-ключ предприятия из iikoWeb: «Интеграции → API-ключи» либо «Настройки Cloud API → Добавить интеграцию» — название раздела зависит от версии кабинета. Дайте ему доступ только к нужной организации. В старых инструкциях этот ключ называется `apiLogin`.
4. Внешнее меню для сайта: категории, позиции, актуальные цены, фото, вес, состав и обязательные модификаторы.
5. Для приёма заказов: терминальную группу, работающий модуль доставки, правила зон/стоимости доставки, доступные способы оплаты. Для брони — залы, столы и правила времени резервирования. Для бонусов — настроенную программу и собственную ссылку регистрации карты «Ялты».

Ключи передаются разработчику через защищённое хранилище секретов, а не публичный GitHub, клиентский JavaScript или переписку с открытым доступом. Сначала подключаем только чтение меню, затем проверяем заказы на тестовом предприятии.

## Где будет работать интеграция

[GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages) публикует статические HTML, CSS и JavaScript. На нём можно разместить этот интерфейс, но нельзя запустить сервер интеграции или безопасно хранить iiko-ключи. Для реальных заказов потребуется отдельный HTTPS backend и база данных.

```text
Браузер гостя → сайт React / GitHub Pages
                     ↓ HTTPS
              API сервера «Ялты»
              ├── база пользователей, заказов и броней
              ├── подтверждение телефона и сессии
              ├── iiko Cloud API
              └── платёжный провайдер, если нужна онлайн-оплата

iiko → защищённый webhook сервера → сохранённый статус → личный кабинет
```

Практичная схема развёртывания: сайт остаётся на GitHub Pages на этапе демонстрации, сервер работает на отдельном хостинге с HTTPS и секретами в настройках окружения. После выбора домена интерфейс переносится на основной адрес, API — на `api.<домен>`. Можно разместить оба компонента на одном сервере. Хостинг, регион хранения персональных данных и платёжного провайдера выбирают перед промышленным запуском.

`VITE_*` — публичные переменные сборки. В них допустим только URL собственного API, например `VITE_API_URL`. Никакие ключи iiko, токены, SMS-секреты или приватные данные туда не добавляются.

## Получение меню: последовательность запросов

Все перечисленные запросы выполняет backend. Базовый адрес российского API: `https://api-ru.iiko.services`.

### 1. Авторизация

Актуальный метод — `POST /api/v2/access_token`, тело содержит `appId`, `clientSecret`, `apiKey`. Полученный `token` используется как `Authorization: Bearer <token>`. Согласно документации токен действует один час; сервер переиспользует его и обновляет перед истечением. Старый `POST /api/1/access_token` с `apiLogin` считается устаревшим: для новой интеграции ориентируемся на v2, а совместимость существующего ключа уточняем по настройкам тестового предприятия. [Авторизация iiko](https://api.iiko.help/docs/concepts/authorization/).

### 2. Организация и терминальная группа

`POST /api/1/organizations` с пустым объектом возвращает доступные организации. Сохраняем ID выбранного тестового ресторана. Для доставки дополнительно получаем терминальные группы через `POST /api/1/terminal_groups`; выбор группы должен соответствовать кассе, которая принимает веб-заказы. [Быстрый старт](https://api.iiko.help/quickstart), [создание доставки](https://api.iiko.help/docs/guides/create-delivery-order/).

### 3. Внешнее меню

| Запрос | Назначение |
| --- | --- |
| `POST /api/2/menu` | Список внешних меню и ценовых категорий |
| `POST /api/menu/v3/by_id` | Содержимое выбранного меню |

Для второго запроса нужны `externalMenuId` и **`organizationId` в единственном числе**; `priceCategoryId` добавляется, если используются отдельные цены для доставки. Старый `/api/2/menu/by_id` помечен как устаревший. Если список меню пустой, сначала создаём внешнее меню в iikoWeb. [Внешнее меню iiko](https://api.iiko.help/docs/guides/external-menu/).

Backend преобразует ответ в модель карточек сайта: категории, названия, описания, цены, изображения, вес, размеры, модификаторы и доступность. Для отправки в кассу сохраняем настоящий `productId` и соответствующие ID размеров/модификаторов; демонстрационные ID сайта для этого непригодны. Обязательные модификаторы нельзя молча игнорировать. Меню кэшируем на сервере; период обновления согласуем с действующими лимитами API.

### 4. Стоп-лист

`POST /api/1/stop_lists` возвращает недоступные позиции, а `POST /api/1/stop_lists/check` позволяет проверить выбранные товары непосредственно перед заказом. Проверка учитывает нужную организацию и терминальную группу. Если доступность изменилась, показываем гостю обновление корзины до оформления. [Стоп-листы iiko](https://api.iiko.help/docs/guides/stop-lists/).

## Как оформить настоящий заказ

Предлагаемый контракт нашего backend:

| Маршрут сайта | Поведение сервера |
| --- | --- |
| `GET /api/menu` | Возвращает нормализованное меню из кэша |
| `POST /api/checkout/quote` | Проверяет адрес, наличие, модификаторы и пересчитывает итог |
| `POST /api/orders` | Создаёт один заказ, возвращает его ID и статус обработки |
| `GET /api/me/orders` | Возвращает только заказы текущего пользователя |
| `GET /api/me/orders/:id` | Проверяет владельца и возвращает детали доставки |
| `POST /api/reservations` | Принимает запрос на бронь и проверяет результат iiko |

Это спецификация для следующего этапа, а не уже работающие маршруты проекта.

Backend повторно рассчитывает цены по своему каталогу и не доверяет сумме из браузера. Проверяет адрес, время работы, количество, размеры, модификаторы, наличие и согласие гостя. Для географии доставки есть `POST /api/1/delivery_restrictions/allowed`.

Доставка создаётся через `POST /api/1/deliveries/create`: организация, терминальная группа, телефон, позиции и данные гостя; для курьера нужен адрес. `DeliveryByCourier` означает доставку, `DeliveryByClient` — самовывоз. Формат адреса выбирается по настройке организации, а не жёстко задаётся один для всех ресторанов.

На каждое оформление сервер заранее создаёт устойчивый UUID заказа. Повтор запроса после сетевой ошибки использует тот же ID, чтобы не породить дубль. `correlationId` сохраняется для проверки асинхронной обработки через `POST /api/1/commands/status`. Успешный HTTP-ответ ещё не означает, что заказ принят кассой. [Создание доставки iiko](https://api.iiko.help/docs/guides/create-delivery-order/).

Онлайн-оплата подключается отдельно. Платёж считается успешным только после серверной проверки у провайдера, а не после перехода браузера на страницу успеха. Если онлайн-оплаты пока нет, интерфейс должен предлагать только действительно доступный способ оплаты при получении.

## Личный кабинет и статусы

Подтверждённый телефон связывается с пользователем в нашей базе. Вход по телефону требует настоящего SMS/звонка, ограничения частоты и серверной сессии. Демо-профиль в браузере не является авторизацией. API кабинета проверяет владельца заказа; поиск по произвольному введённому телефону нельзя отдавать публично.

Текущие детали заказа доступны через `POST /api/1/deliveries/by_id`. Для восстановления пропущенных обновлений можно использовать `POST /api/1/deliveries/by_revision` с сохранённой ревизией. [Получение заказов iiko](https://api.iiko.help/docs/guides/get-orders/).

Для оперативных изменений настраиваем `POST /api/1/webhooks/update_settings`, предварительно прочитав `POST /api/1/webhooks/settings`: у организации один URL webhook, поэтому нельзя затереть действующую интеграцию. При необходимости наш сервер распределяет события нескольким потребителям.

Сервер проверяет `Authorization` входящего webhook по настроенному `authToken`, сохраняет события и быстро отвечает `200`. Обрабатываем повторные события идемпотентно. `DeliveryOrderUpdate` обновляет заказ, `DeliveryOrderError` фиксирует ошибку. `StopListUpdate` сообщает о необходимости повторно запросить стоп-лист; сам список в событии не содержится. [Вебхуки iiko](https://api.iiko.help/docs/guides/webhooks/).

Гость видит реальные этапы: «Передаём заказ», «Принят», «Готовится», «В пути», «Доставлен» или объяснение ошибки/отмены. Время обновления показывается отдельно; при потере связи не имитируем прогресс таймером.

## Бронирование столов

Получаем залы и столы через `POST /api/1/reserve/available_restaurant_sections`, проверяем занятость через `POST /api/1/reserve/restaurant_sections_workload`, затем создаём резерв через `POST /api/1/reserve/create`. Нужны ID столов, будущие дата/время, длительность, контакты и число гостей. Результат проверяем через `POST /api/1/reserve/status_by_id` и события резервов. [Бронирование iiko](https://api.iiko.help/docs/guides/table-reservations/).

До подключения кассы форма может собирать только заявку с явно указанным статусом «Ожидает подтверждения». Надпись «Стол забронирован» допустима после реального подтверждения. В текущем демо заявки сохраняются исключительно локально и ресторану не передаются.

## Лояльность

Сначала согласуем правила «Ялты»: размер бонусов, исключения, сроки и каналы применения. Затем используем `POST /api/1/loyalty/iiko/program` для списка программ, `/customer/info` для гостя, `/customer/create_or_update` для создания/обновления и `/calculate` для расчёта заказа. У последних трёх методов общий префикс `/api/1/loyalty/iiko`. [Лояльность iiko](https://api.iiko.help/docs/guides/loyalty/).

Регистрация цифровой карты требует собственной ссылки или QR-кода поставщика карт для «Ялты». API iiko само по себе не создаёт Apple Wallet / Google Wallet пропуск. Кнопку выдачи карты подключаем после получения этой ссылки; стороннюю ссылку «Софико» использовать нельзя. Баланс и начисления отображаем из сервера, а не записываем вручную в браузер.

Инструкция на странице лояльности адаптирована из указанного референса: открыть ссылку или QR, подтвердить телефон SMS-кодом, заполнить обязательные поля анкеты, после появления карты выбрать «Добавить». Сам процесс регистрации зависит от будущего поставщика карт «Ялты»; после его подключения проверяем названия кнопок на iOS и Android. [Исходная инструкция «Софико»](https://soficorestaurant.ru/loyalty).

## Проверка перед запуском

- Меню отображает категории, реальные фото, корректные цены и обязательные модификаторы; обновление в iiko попадает на сайт.
- Позиция из стоп-листа не оформляется, даже если была добавлена в корзину до изменения наличия.
- Доставка и самовывоз корректно попадают на тестовую кассу; адрес вне зоны получает понятный отказ.
- Повтор нажатия или сетевой таймаут не создаёт второй заказ.
- Ошибка кассы отображается как ошибка, а не как подтверждённый заказ.
- Webhook с неверной авторизацией отвергается; повторный корректный webhook не дублирует запись.
- Пользователь A не может получить заказ/адрес пользователя B изменением URL или телефона.
- Проверены SMS, завершение сессии, восстановление доступа, ограничение запросов и серверное хранение данных.
- Бронь проверяет будущую дату, часы работы и реальную занятость; подтверждение поступает из ресторана.
- Подключены действующие контакты, условия доставки, собственные фото и утверждённые правила программы лояльности.
- Секретов нет в репозитории, клиентской сборке, логах, URL и аналитике.

Для начала интеграции достаточно подготовить доступ к тестовому iikoWeb, параметры приложения, API-ключ и внешнее меню. Первый проверяемый результат — реальные блюда тестового ресторана на странице доставки. Только затем включаем отправку заказов, статусы, брони и лояльность.
