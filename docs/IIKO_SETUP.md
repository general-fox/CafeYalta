# Подключение «Ялты» к iiko

В проекте работают локальное чтение меню iiko и отправка тестовых заказов на самовывоз и курьерскую доставку. **25 ноября 2026 года проверены организация «Мой ресторан», касса «Офис» и внешнее меню «Сайт Ялта тест» с ценовой категорией «Доставка»: 7 категорий, 37 доступных для заказа карточек, у 7 составных блюд есть выбор добавок, фотография есть у одной карточки.** Через локальный интерфейс iiko принял на «Офис» заказ №1 — борщ за 200 ₽, самовывоз, и заказ №2 — куриный суп за 200 ₽, курьерская доставка с адресом. Выбраны наличные при получении; списаний и платы за доставку не было. Это подтверждает создание заказов в iiko, но не фактическую доставку курьером и не готовность боевых тарифов.

Публичная демонстрация на GitHub Pages автоматически не меняется: в ней используется статический каталог, заказы и брони в кафе не отправляются. Ниже отдельно описаны реализованные локальные сценарии и план промышленного запуска, кабинета, бронирования и лояльности. Контракт адреса и параметры организации сверены с [официальной OpenAPI iiko](https://api-ru.iiko.services/api-docs/docs) 25 ноября 2026 года.

## Этап 1 — локально прочитать меню

Все команды выполняются из корневой папки проекта. Нужны Node.js 22 и установленные зависимости (`npm install`).

### 1. Сохраните ключи только на своём компьютере

Скопируйте `server/.env.example` в `server/.env`, если локального файла ещё нет, и заполните три значения:

```dotenv
IIKO_APP_ID=
IIKO_CLIENT_SECRET=
IIKO_API_KEY=
```

`IIKO_APP_ID` и `IIKO_CLIENT_SECRET` относятся к приложению разработчика, `IIKO_API_KEY` — к предприятию в iikoWeb. Если данных приложения ещё нет, зарегистрируйтесь и создайте приложение по [официальной инструкции iiko](https://api.iiko.help/quickstart). API-ключ создаётся отдельно в iikoWeb.

Файл `server/.env` исключён из Git. Не отправляйте ключи в чат, не добавляйте их в репозиторий, `public/` или переменные `VITE_*`. Вводите значения непосредственно в локальный файл, а не в команду терминала.

### 2. Найдите свою организацию и меню

```powershell
npm run iiko:check
```

Команда обращается к iiko и выводит доступные организации, внешние меню и ценовые категории, без ключей и токенов. Выберите нужное тестовое предприятие и меню. Дополните тот же `server/.env` их идентификаторами:

```dotenv
IIKO_ORGANIZATION_ID=
IIKO_EXTERNAL_MENU_ID=
IIKO_PRICE_CATEGORY_ID=
```

Для текущего демо выберите организацию «Мой ресторан», внешнее меню «Сайт Ялта тест» и **обязательно заполните `IIKO_PRICE_CATEGORY_ID` идентификатором категории «Доставка»**: чтение этого меню проверено именно с ней. У другого ресторана ценовая категория может быть необязательной — это зависит от настройки меню и цен. Если меню не найдено, проверьте права API-ключа и наличие внешнего меню в iikoWeb.

### 3. Запустите локальный API

```powershell
npm run api
```

Адрес — `http://127.0.0.1:3001` (локальный порт 3001). Сервер всегда привязан к `127.0.0.1`, поэтому недоступен с других устройств. После изменения `.env` перезапустите его; остановка — `Ctrl+C`.

### 4. Проверьте результат

| Локальный запрос | Что он показывает |
| --- | --- |
| [GET /api/health](http://127.0.0.1:3001/api/health) | Статус заполнения настроек без секретов. Запрос к iiko не выполняет и реальное соединение не подтверждает. |
| [GET /api/menu](http://127.0.0.1:3001/api/menu) | Категории и карточки внешнего меню iiko v3 вместе с исходным снимком `data`. Кэш на 15 секунд; `?refresh=1` принудительно обновляет меню. Без явного включения заказов — `orderingEnabled: false`. |

Чтение нового меню и работа локального API проверены 25 ноября 2026 года. Публичная версия на GitHub Pages автоматически не переключается. Локальный интерфейс использует iiko только при `VITE_CATALOG_SOURCE=iiko`.

При `IIKO_ORDERING_ENABLED=false` сервер только читает меню, **заказы не отправляются**. Заказы включаются отдельно на этапе 2. Запись броней и бонусов в iiko, новая авторизация гостей и платежи пока не подключены. Локальный API не нужно открывать в интернет.

## Этап 2 — тестовый самовывоз и доставка в демо-iikoFront

Для контрольного заказа достаточно одной доступной простой позиции текущего внешнего меню. Для полного запуска каждая продаваемая позиция должна существовать в номенклатуре iiko, иметь актуальную цену и входить во внешнее меню. Уже существующие карточки используют повторно. Данные статических демонстрационных карточек сайта не являются подтверждёнными ценами или составом кафе.

В `server/.env` дополнительно заполните `IIKO_TERMINAL_GROUP_ID` идентификатором группы «Офис» и установите `IIKO_ORDERING_ENABLED=true`. В корне проекта создайте игнорируемый `.env.development.local` только с публичным флагом `VITE_CATALOG_SOURCE=iiko`; ключей в нём быть не должно. После изменения файлов перезапустите `npm run api` и `npm run dev`. Vite перенаправляет локальные запросы `/api` на порт 3001. Обычная production-сборка без этого флага остаётся демонстрационной.

Включённый режим предлагает самовывоз и курьерскую доставку с наличными при получении. **В тесте оплачиваются только блюда.** Автоматический подарочный морс, демонстрационные минимум 800 ₽ и тариф 199 ₽ здесь не применяются. Проверка боевых зон, минимальной суммы, тарифов и часов доставки не реализована. Позиции с неподдерживаемыми обязательными модификаторами или составной схемой нельзя добавить в заказ. При отсутствии фотографии отображается нейтральная заглушка.

Для доставки сервер читает актуальный `addressFormatType` организации. У демо-предприятия это `Legacy`: в форме нужны город, улица и дом, необязательны квартира, подъезд, этаж и домофон. В iiko передаётся адрес с `type: "legacy"`, `street: { name, city }` и `house`; справочные ID улицы для этого варианта не требуются. Формат `City` поддерживает строку `line1`. Неизвестный формат отключает доставку с понятным сообщением; самовывоз остаётся доступен. Формат и заполнение полей проверяются до отправки, но это не проверка существования адреса или попадания в зону обслуживания.

`POST /api/orders` принимает идентификаторы карточек и количества, контакты тестового гостя, способ получения `pickup`/`delivery`, адрес для доставки, ожидаемую сумму и устойчивый `requestId`. Сервер заново получает каталог, рассчитывает цену, проверяет кассу, соответствующий тип заказа, наличную оплату и стоп-лист. До запроса в iiko он сохраняет заявку в игнорируемой папке `server/.data/orders/`. Там хранятся состав и статус, хеш доступа и хеш запроса; контакты, адрес гостя и исходный токен не сохраняются. Способ получения и адрес входят в хеш запроса. Повтор той же заявки не вызывает повторное создание заказа; изменение данных с прежним `requestId` отклоняется.

`GET /api/orders/:requestId` требует того же случайного токена доступа в `Authorization: Bearer ...`. Успешный HTTP-ответ iiko сам по себе не означает приём: сайт показывает «Передаём заказ», пока сервер не подтвердит результат. При потере связи заявка сохраняется, а новый заказ автоматически не создаётся. Корзина очищается только после подтверждения.

Контрольная проверка: открыть локальное меню, добавить одну доступную позицию, указать вымышленные контакты и оформить самовывоз; затем отдельным заказом проверить доставку с тестовым адресом. **Каждое подтверждение действительно создаёт заказ в демо-кафе.** Проверить результат на кассе «Офис» и подтверждение сайта. 25 ноября оба сценария завершились приёмом iiko: №1 — борщ за 200 ₽, самовывоз; №2 — куриный суп за 200 ₽, доставка. Автоматические тесты используют имитацию API и сами заказов не создают. Сервер остаётся доступен только на текущем компьютере; для публичного приёма понадобятся размещение, полноценная авторизация и эксплуатационные настройки.

### Выбор модификаторов — дополнение от 25 ноября 2026 года

Все 37 карточек текущего меню доступны; у четырёх чебуреков можно выбрать соусы, у трёх видов мороженого — варенье. Каждая из этих семи карточек имеет четыре необязательные добавки: не более одной порции каждой и четырёх суммарно. Текущая цена каждой добавки в iiko — 200 ₽; бесплатное количество равно нулю. Эти значения берутся из API, а не закреплены в интерфейсе.

Карточка блюда показывает обязательные и необязательные группы, значения по умолчанию, цены и ограничения количества из меню iiko. Одинаковые блюда с разными добавками становятся разными строками корзины. Выбор можно отредактировать; названия добавок, количества и сумма сохраняются в истории принятого заказа. Обновление меню перепроверяет корзину, но не переписывает уже отправленный заказ.

Каждая строка запроса `POST /api/orders` передаёт `id`, `quantity` и `selections: [{ groupId, modifierId, quantity }]`, где количество добавки относится к одной порции блюда. Сервер проверяет выбор по свежему каталогу: неизвестные или повторяющиеся идентификаторы, неверные количества и нарушение обязательности/лимитов отклоняются. Цены добавок и итог вычисляются на сервере; изменившаяся сумма требует обновить корзину до отправки. Проверка стоп-листа получает тот же состав, который готовится к передаче на кассу.

Поддерживаются обычные `Product` и целые составные `Compound` с одним основным компонентом. Половинки не предлагаются. Бесплатные количества (`freeQuantity > 0`), независимые (`independentQuantity`) и дробные количества пока не поддерживаются; блюда с такими настройками или непроверяемой схемой/ценой отображаются недоступными с причиной. Скрытый обязательный модификатор или скрытый выбор по умолчанию тоже блокирует блюдо. Для полного меню боевого ресторана сначала проверяют его фактические схемы. Формат сверялся с [официальным руководством по модификаторам](https://api.iiko.help/docs/en/guides/modifiers/) и [OpenAPI](https://api-ru.iiko.services/api-docs/docs).

На этом этапе живой `/api/1/stop_lists/check` принял две порции чебурека с курицей, каждая с одной порцией сацебели, общей стоимостью **800 ₽**. `/api/1/deliveries/create` для такого состава проверен только на имитации API. **Новых живых заказов с модификаторами не создавали**; результаты двух ранее принятых простых заказов №1 и №2 остаются отдельной проверкой. При следующем согласованном тесте нужно подтвердить состав и сумму заказа с добавками непосредственно в iikoFront.

## Что подготовить для следующих этапов

1. Доступ администратора к iikoWeb тестового предприятия и название организации, из которой будем брать блюда.
2. Приложение на [портале разработчика iiko](https://api.iiko.help/quickstart): `appId` и `clientSecret`.
3. API-ключ предприятия из iikoWeb: «Интеграции → API-ключи» либо «Настройки Cloud API → Добавить интеграцию» — название раздела зависит от версии кабинета. Дайте ему доступ только к нужной организации. В старых инструкциях этот ключ называется `apiLogin`.
4. Внешнее меню для сайта: категории, позиции, актуальные цены, фото, вес, состав и обязательные модификаторы.
5. Для приёма заказов: терминальную группу, работающий модуль доставки, правила зон/стоимости доставки, доступные способы оплаты. Для брони — залы, столы и правила времени резервирования. Для бонусов — настроенную программу и собственную ссылку регистрации карты «Ялты».

Ключи передаются разработчику через защищённое хранилище секретов, а не публичный GitHub, клиентский JavaScript или переписку с открытым доступом. Чтение меню, тестовый самовывоз и доставку проверяем по этапам выше; промышленный запуск и остальные сценарии настраиваются отдельно.

## Будущее размещение интеграции

[GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages) публикует статические HTML, CSS и JavaScript. На нём можно разместить этот интерфейс, но нельзя запустить сервер интеграции или безопасно хранить iiko-ключи. Для реальных заказов потребуется отдельный HTTPS backend и база данных.

```text
Браузер гостя → сайт React / GitHub Pages
                     ↓ HTTPS
              API сервера «Ялты»
              ├── база пользователей, заказов и броней
              ├── подтверждение телефона и сессии
              ├── iiko Cloud API
              └── платёжный провайдер, если нужна онлайн-оплата

iiko → защищённый webhook сервера → сохранённый статус → личный кабинет
```

Практичная схема развёртывания: сайт остаётся на GitHub Pages на этапе демонстрации, сервер работает на отдельном хостинге с HTTPS и секретами в настройках окружения. После выбора домена интерфейс переносится на основной адрес, API — на `api.<домен>`. Можно разместить оба компонента на одном сервере. Хостинг, регион хранения персональных данных и платёжного провайдера выбирают перед промышленным запуском.

`VITE_*` — публичные переменные сборки. В них допустим только URL собственного API, например `VITE_API_URL`. Никакие ключи iiko, токены, SMS-секреты или приватные данные туда не добавляются.

## Получение меню: последовательность запросов

Авторизация, список организаций, внешнее меню, преобразование каталога, терминальные группы и проверка стоп-листа уже используются локальным сервером. Все запросы к iiko выполняет backend. Базовый адрес российского API: `https://api-ru.iiko.services`.

### 1. Авторизация

Актуальный метод — `POST /api/v2/access_token`, тело содержит `appId`, `clientSecret`, `apiKey`. Полученный `token` используется как `Authorization: Bearer <token>`. Согласно документации токен действует один час; сервер переиспользует его и обновляет перед истечением. Старый `POST /api/1/access_token` с `apiLogin` считается устаревшим: для новой интеграции ориентируемся на v2, а совместимость существующего ключа уточняем по настройкам тестового предприятия. [Авторизация iiko](https://api.iiko.help/docs/concepts/authorization/).

### 2. Организация и терминальная группа

`POST /api/1/organizations` с пустым объектом возвращает доступные организации. Сохраняем ID выбранного тестового ресторана. Запрос с `organizationIds` и `returnAdditionalInfo: true` возвращает настройку `addressFormatType`; именно она определяет формат адреса доставки. Для заказов дополнительно получаем терминальные группы через `POST /api/1/terminal_groups`; выбор группы должен соответствовать кассе, которая принимает веб-заказы. В текущем демо выбрана «Офис», её доступность проверена через `/api/1/terminal_groups/is_alive`. [Быстрый старт](https://api.iiko.help/quickstart), [официальная OpenAPI](https://api-ru.iiko.services/api-docs/docs).

### 3. Внешнее меню

| Запрос | Назначение |
| --- | --- |
| `POST /api/2/menu` | Список внешних меню и ценовых категорий |
| `POST /api/menu/v3/by_id` | Содержимое выбранного меню |

Для второго запроса нужны `externalMenuId` и **`organizationId` в единственном числе**; `priceCategoryId` добавляется, если используются отдельные цены для доставки. Для текущего меню «Сайт Ялта тест» категория «Доставка» обязательна. Старый `/api/2/menu/by_id` помечен как устаревший. Если список меню пустой, сначала создаём внешнее меню в iikoWeb. [Внешнее меню iiko](https://api.iiko.help/docs/guides/external-menu/).

Локальный API преобразует меню v3 в категории и карточки сайта и кэширует его на 15 секунд. Открытая видимая страница автоматически повторяет чтение через 15 секунд после предыдущего ответа, а также при возвращении во вкладку и восстановлении сети. Фоновое чтение использует общий серверный кэш; ручное `?refresh=1` остаётся доступным. Фото, цены и состав обновляются без F5; это происходит после появления изменений в API iiko. Неизменившийся каталог не пересоздаёт карточки и не сбрасывает прокрутку. При сбое сохраняются последние карточки, но оформление блокируется до успешной синхронизации. Для отправки в кассу сохраняются настоящий `productId` и соответствующий ID размера; обязательные модификаторы проверяются вместе с выбранными добавками, а неподдерживаемые схемы блокируют позицию. Состав и сумма уже отправленного заказа не меняются при обновлении меню. Перед публичным запуском частоту опроса согласуем с действующими лимитами API.

### 4. Стоп-лист

`POST /api/1/stop_lists` возвращает недоступные позиции, а `POST /api/1/stop_lists/check` позволяет проверить выбранные товары непосредственно перед заказом. Проверка учитывает нужную организацию и терминальную группу. Если доступность изменилась, показываем гостю обновление корзины до оформления. [Стоп-листы iiko](https://api.iiko.help/docs/guides/stop-lists/).

| --- | --- |
| `GET /api/menu` | Реализовано: нормализованный каталог, исходный снимок v3 и настройки доступных способов получения/формата адреса |
| `POST /api/checkout/quote` | План: проверка зоны, тарифов, минимума и предварительный расчёт заказа |
| `POST /api/orders` | Реализовано локально для тестового самовывоза и доставки; возвращает ID и статус обработки |
| `GET /api/orders/:requestId` | Реализовано локально: статус своей заявки по случайному токену доступа |
| `GET /api/me/orders` | План: только заказы подтверждённого пользователя |
| `GET /api/me/orders/:id` | План: проверка владельца и детали доставки |
| `POST /api/reservations` | План: запрос на бронь и проверка результата iiko |

Без явного включения заказов сервер только читает меню. В этапе 2 дополнительно работают `POST /api/orders` и защищённый токеном `GET /api/orders/:requestId`. Предварительный расчёт отдельным маршрутом, серверный кабинет и бронирование — спецификация будущей разработки.

Backend повторно рассчитывает цены по свежему каталогу и не доверяет сумме из браузера. Уже проверяются количество, соответствующий ID размера, выбор и ограничения модификаторов, поддерживаемая схема составного блюда, стоп-лист, доступность кассы и поля адреса в формате организации. Проверку часов приёма, зон, минимальной суммы и тарифа ещё нужно реализовать и испытать. Для географии доставки предусмотрен `POST /api/1/delivery_restrictions/allowed`; в текущем сценарии он не используется.

Заказ создаётся через `POST /api/1/deliveries/create`: организация, терминальная группа, телефон, позиции и данные гостя; для курьера нужен адрес. Сервер выбирает `orderTypeId` из фактического справочника организации: у текущего демо `orderServiceType: DeliveryPickUp` соответствует самовывозу, `DeliveryByCourier` — курьерской доставке. Формат адреса берётся из настройки организации; у проверенного демо это `Legacy`.

На каждое оформление сервер заранее создаёт устойчивый UUID заказа. Повтор запроса после сетевой ошибки использует тот же ID, чтобы не породить дубль. `correlationId` сохраняется для проверки асинхронной обработки через `POST /api/1/commands/status`. Успешный HTTP-ответ ещё не означает, что заказ принят кассой. [Создание доставки iiko](https://api.iiko.help/docs/guides/create-delivery-order/).

Онлайн-оплата подключается отдельно. Платёж считается успешным только после серверной проверки у провайдера, а не после перехода браузера на страницу успеха. Если онлайн-оплаты пока нет, интерфейс должен предлагать только действительно доступный способ оплаты при получении.

## Будущий этап — личный кабинет и статусы доставки

Сейчас локальный сайт подтверждает создание заказа по ответам iiko и сохраняет историю в браузере. Серверный статус отдельной заявки защищён случайным токеном. Полноценного кабинета с подтверждённой личностью и обновлением этапов приготовления/доставки ещё нет; далее описан план.

Подтверждённый телефон связывается с пользователем в нашей базе. Вход по телефону требует настоящего SMS/звонка, ограничения частоты и серверной сессии. Демо-профиль в браузере не является авторизацией. API кабинета проверяет владельца заказа; поиск по произвольному введённому телефону нельзя отдавать публично.

Текущие детали заказа доступны через `POST /api/1/deliveries/by_id`. Для восстановления пропущенных обновлений можно использовать `POST /api/1/deliveries/by_revision` с сохранённой ревизией. [Получение заказов iiko](https://api.iiko.help/docs/guides/get-orders/).

Для оперативных изменений настраиваем `POST /api/1/webhooks/update_settings`, предварительно прочитав `POST /api/1/webhooks/settings`: у организации один URL webhook, поэтому нельзя затереть действующую интеграцию. При необходимости наш сервер распределяет события нескольким потребителям.

Сервер проверяет `Authorization` входящего webhook по настроенному `authToken`, сохраняет события и быстро отвечает `200`. Обрабатываем повторные события идемпотентно. `DeliveryOrderUpdate` обновляет заказ, `DeliveryOrderError` фиксирует ошибку. `StopListUpdate` сообщает о необходимости повторно запросить стоп-лист; сам список в событии не содержится. [Вебхуки iiko](https://api.iiko.help/docs/guides/webhooks/).

Гость видит реальные этапы: «Передаём заказ», «Принят», «Готовится», «В пути», «Доставлен» или объяснение ошибки/отмены. Время обновления показывается отдельно; при потере связи не имитируем прогресс таймером.

## Будущий этап — бронирование столов

Получаем залы и столы через `POST /api/1/reserve/available_restaurant_sections`, проверяем занятость через `POST /api/1/reserve/restaurant_sections_workload`, затем создаём резерв через `POST /api/1/reserve/create`. Нужны ID столов, будущие дата/время, длительность, контакты и число гостей. Результат проверяем через `POST /api/1/reserve/status_by_id` и события резервов. [Бронирование iiko](https://api.iiko.help/docs/guides/table-reservations/).

До подключения кассы форма может собирать только заявку с явно указанным статусом «Ожидает подтверждения». Надпись «Стол забронирован» допустима после реального подтверждения. В текущем демо заявки сохраняются исключительно локально и ресторану не передаются.

## Будущий этап — лояльность

Сначала согласуем правила «Ялты»: размер бонусов, исключения, сроки и каналы применения. Затем используем `POST /api/1/loyalty/iiko/program` для списка программ, `/customer/info` для гостя, `/customer/create_or_update` для создания/обновления и `/calculate` для расчёта заказа. У последних трёх методов общий префикс `/api/1/loyalty/iiko`. [Лояльность iiko](https://api.iiko.help/docs/guides/loyalty/).

Регистрация цифровой карты требует собственной ссылки или QR-кода поставщика карт для «Ялты». API iiko само по себе не создаёт Apple Wallet / Google Wallet пропуск. Кнопку выдачи карты подключаем после получения этой ссылки; стороннюю ссылку «Софико» использовать нельзя. Баланс и начисления отображаем из сервера, а не записываем вручную в браузер.

Инструкция на странице лояльности адаптирована из указанного референса: открыть ссылку или QR, подтвердить телефон SMS-кодом, заполнить обязательные поля анкеты, после появления карты выбрать «Добавить». Сам процесс регистрации зависит от будущего поставщика карт «Ялты»; после его подключения проверяем названия кнопок на iOS и Android. [Исходная инструкция «Софико»](https://soficorestaurant.ru/loyalty).

## Проверка перед запуском

Это список требований для промышленного запуска, а не отчёт о пройденных проверках. Локально подтверждены чтение меню и приём двух контрольных заказов; зоны, тарифы, минимум, SMS, webhooks, бронирование и лояльность ещё не проверены как рабочие интеграции.

- Меню отображает категории, реальные фото, корректные цены и обязательные модификаторы; обновление в iiko попадает на сайт.
- Позиция из стоп-листа не оформляется, даже если была добавлена в корзину до изменения наличия.
- Доставка и самовывоз корректно попадают на тестовую кассу; адрес вне зоны получает понятный отказ.
- Повтор нажатия или сетевой таймаут не создаёт второй заказ.
- Ошибка кассы отображается как ошибка, а не как подтверждённый заказ.
- Webhook с неверной авторизацией отвергается; повторный корректный webhook не дублирует запись.
- Пользователь A не может получить заказ/адрес пользователя B изменением URL или телефона.
- Проверены SMS, завершение сессии, восстановление доступа, ограничение запросов и серверное хранение данных.
- Бронь проверяет будущую дату, часы работы и реальную занятость; подтверждение поступает из ресторана.
- Подключены действующие контакты, условия доставки, собственные фото и утверждённые правила программы лояльности.
- Секретов нет в репозитории, клиентской сборке, логах, URL и аналитике.

Результат на 25 ноября 2026 года — новое меню и выбор поддерживаемых добавок подключены к локальному сайту, два простых заказа на самовывоз и курьерскую доставку приняты iiko на кассу «Офис». Для промышленного запуска остаются размещение backend, правила зон/минимума/тарифов и часов работы, проверка заказа с добавками на кассе и специальных схем меню, серверная авторизация и статусы доставки; брони, лояльность и онлайн-оплата подключаются отдельно.
