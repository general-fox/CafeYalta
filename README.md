# Кафе «Ялта»

Адаптивный многостраничный интерфейс кафе в Москве: главная, меню доставки, корзина, оформление заказа, личный кабинет, программа лояльности и всплывающая форма бронирования. Основной цвет — `#334da0`, красный акцент — `#a63c36`; логотипы подготовлены без теней. Главная открывается сгенерированной фотографией с мягким параллаксом; при уменьшенной анимации в настройках устройства эффект отключается.

По умолчанию это интерактивная демонстрационная версия. Меню, цены, адрес, телефон, время работы и условия доставки служат примерами. В этом режиме заказы и брони **не отправляются в ресторан**. Отдельный локальный режим iiko, описанный ниже, позволяет отправлять тестовые заказы на самовывоз и курьерскую доставку в демо-кафе. Деньги не списываются, SMS не отправляются, телефон не подтверждается. Профиль, корзина и история сохраняются в `localStorage` конкретного браузера: это не настоящая авторизация. Для проверки используйте вымышленные данные. Очистка данных сайта в браузере удаляет локальную историю.

## Локальный запуск

Нужны Node.js 22 и npm. Из папки проекта выполните:

```powershell
npm install
npm run dev
```

Откройте [http://localhost:5180](http://localhost:5180). Порт закреплён через `strictPort`: если 5180 занят, Vite сообщает об ошибке и не переключается незаметно на другой порт. Остановите прежний сервер или освободите порт, затем повторите запуск. Сервер слушает только локальный интерфейс.

```powershell
npm test
npm run build
npm run preview
```

- `npm test` проверяет расчёты корзины, доставку, телефон и время бронирования, а также локальный API и клиент iiko на имитированных ответах, без обращения к предприятию.
- `npm run build` создаёт production-сборку в `dist`.
- `npm run preview` показывает готовую сборку по адресу [http://localhost:4173](http://localhost:4173); порт также фиксирован. Сначала выполните сборку.

## Проверка сценариев статической демонстрации

1. На главной нажмите «Заказать доставку». Выберите категорию меню, откройте карточку блюда и добавьте его в корзину.
2. Измените количество в корзине. Для курьерской доставки минимум — 800 ₽, стоимость — 199 ₽ при любой сумме заказа; самовывоз без минимума и без платы за доставку. При доставке от 2 000 ₽ автоматически добавляется один морс в подарок. Эти условия демонстрационные.
3. Оформите тестовый заказ с вымышленными контактами. Откройте кабинет: там появятся состав, сумма и адрес, а также явная отметка тестового статуса.
4. Нажмите «Забронировать стол», выберите будущую дату и время. Тестовая заявка появится в разделе бронирований кабинета при входе с тем же телефоном.
5. Проверьте страницу лояльности. Инструкция адаптирована под «Ялту»; настоящая регистрация карты подключается после получения собственной ссылки поставщика карт.
6. Повторите сценарии на узком экране. На компьютере категории расположены слева, а на телефоне закреплены сверху и прокручиваются к выбранной категории; корзина доступна из закреплённой панели.

## Развёртывание на GitHub Pages

Репозиторий: [general-fox/CafeYalta](https://github.com/general-fox/CafeYalta).

1. Загрузите проект в ветку `main`, включая `package-lock.json` и `.github/workflows/deploy.yml`. Папки `node_modules`, `dist` и файлы секретов загружать не нужно.
2. В репозитории откройте **Settings → Pages → Build and deployment → Source** и выберите **GitHub Actions**.
3. В **Actions** откройте workflow **Deploy to GitHub Pages**. Он запускается при обновлении `main`; также доступен ручной запуск **Run workflow**.
4. Workflow выполняет `npm ci`, `npm test`, `npm run build` и публикует `dist`. Дождитесь успешного задания `deploy`; фактическая ссылка будет в результате deployment.

Ожидаемый адрес после успешного развёртывания: [general-fox.github.io/CafeYalta/](https://general-fox.github.io/CafeYalta/). Этот README сам по себе не подтверждает, что публикация уже выполнена.

Сайт использует `HashRouter`, например `/#/delivery`, `/#/account`, `/#/loyalty`. Так переходы и перезагрузка внутренних страниц работают на статическом GitHub Pages без серверных правил маршрутизации. В Vite настроен относительный `base: './'`, поэтому ресурсы работают и из подпапки `CafeYalta`, и из корня собственного домена.

При переносе на собственный домен задайте его в **Settings → Pages → Custom domain**, настройте DNS у регистратора по [инструкции GitHub](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site) и включите HTTPS после проверки домена. Hash-маршруты можно оставить. Для чистых URL без `#` потребуется хостинг с перенаправлением запросов к приложению и соответствующая смена маршрутизатора.

## iiko: локальное меню, тестовый самовывоз и доставка

Оформление сайта общее для демонстрационного каталога и iiko: главная, шапка, сетки и карточки используют один дизайн. `VITE_CATALOG_SOURCE=iiko` выбирает источник блюд, категорий, цен и фотографий и включает связанное с iiko оформление заказа. Для сохранения дизайна не нужно переключать каталог на `demo`.

**25 ноября 2026 года проверены организация «Мой ресторан», касса «Офис» и внешнее меню «Сайт Ялта тест» с ценовой категорией «Доставка».** Получены 7 категорий и 37 карточек: все 37 доступны для заказа, у 7 составных блюд есть выбор добавок; фотография есть у одной карточки. Через локальный интерфейс iiko принял два контрольных заказа на кассу «Офис»: №1 — борщ за 200 ₽, самовывоз; №2 — куриный суп за 200 ₽, курьерская доставка с адресом. Это проверка создания заказа, без фактической курьерской доставки и списания денег. В обоих случаях выбраны наличные при получении, сумма состоит только из блюда, плата за доставку не добавляется.

Выбор добавок использует обязательность, значения по умолчанию, минимальные и максимальные количества и цены из iiko. Разные варианты одного блюда сохраняются отдельными строками корзины; выбор можно изменить, а принятый состав остаётся в истории заказа. Перед отправкой сервер повторно проверяет выбор и рассчитывает сумму по свежему меню. Составные блюда `Compound` поддерживаются целиком, без половинок. Бесплатные количества (`freeQuantity > 0`), независимые и дробные количества пока не поддерживаются: соответствующее блюдо блокируется с объяснением. У всех 7 текущих блюд `freeQuantity = 0`.

Для нового сценария модификаторов живой `/api/1/stop_lists/check` принял состав из двух чебуреков с курицей, каждый с одним сацебели, на общую сумму 800 ₽. Создание такого заказа через `/api/1/deliveries/create` проверено только на имитации API; новых заказов в iiko на этом этапе не создавали.

Сервер перепроверяет цены, стоп-лист и доступность кассы, сохраняет заявку до отправки и проверяет результат iiko. Публичная демонстрация на GitHub Pages по умолчанию использует статический каталог; локальное подключение iiko её не переключает.

1. Создайте `server/.env` и заполните `IIKO_APP_ID`, `IIKO_CLIENT_SECRET`, `IIKO_API_KEY`. Данные приложения получают на [портале разработчика iiko](https://api.iiko.help/quickstart), API-ключ предприятия — в iikoWeb. `.env` исключён из Git; ключи нельзя отправлять в чат, коммитить или записывать в `VITE_*`.
2. Из корня проекта запустите `npm run iiko:check`. Команда покажет доступные организации, внешние меню и ценовые категории, без секретов. Добавьте выбранные `IIKO_ORGANIZATION_ID` и `IIKO_EXTERNAL_MENU_ID` в тот же `.env`. Для текущего демо-меню «Сайт Ялта тест» обязательно заполните `IIKO_PRICE_CATEGORY_ID` идентификатором категории «Доставка»; для другого ресторана необходимость категории зависит от его настройки цен.
3. Запустите `npm run api`. Сервер работает на локальном порту 3001 с фиксированной привязкой к `127.0.0.1`. После изменения `.env` его нужно перезапустить.
4. Откройте [GET /api/health](http://127.0.0.1:3001/api/health), затем [GET /api/menu](http://127.0.0.1:3001/api/menu).

`/api/health` показывает заполнение настроек и **не проверяет соединение с iiko**. `/api/menu` возвращает категории и карточки блюд из меню v3; кэш — 15 секунд, `?refresh=1` обновляет меню сразу. Без явного включения заказов сервер возвращает `orderingEnabled: false`. Открытая страница автоматически запрашивает меню каждые 15 секунд после завершения предыдущего запроса и при возвращении во вкладку. В скрытой вкладке или без сети опрос приостанавливается. Меню обновляется без перезагрузки страницы; изменения появляются после их публикации в API iiko. При сбое последние карточки остаются видимыми, а оформление отключается до успешного обновления.

Для проверки самовывоза и доставки укажите `IIKO_TERMINAL_GROUP_ID` кассы «Офис» и `IIKO_ORDERING_ENABLED=true` в `server/.env`, а в отдельном игнорируемом `.env.development.local` — только `VITE_CATALOG_SOURCE=iiko`. Запустите `npm run api` и `npm run dev`; откройте [локальное меню](http://localhost:5180/#/delivery). **Кнопка оформления в этом режиме действительно отправляет заказ в демо-iikoFront.** Перед тестом касса должна быть онлайн. Сервер выбирает доступный тип заказа из справочника iiko и формат адреса из настройки организации. У текущего демо формат `Legacy`: обязательны город, улица и дом, дополнительно можно указать квартиру, подъезд, этаж и домофон.

В локальном тесте оплачиваются только блюда наличными при получении. Демонстрационные тариф 199 ₽, минимум 800 ₽ и подарок из статического режима здесь не применяются. Проверка зон доставки, действующих минимумов и тарифов, бронирование в iiko, SMS и онлайн-оплата ещё не подключены. Подробности — [docs/IIKO_SETUP.md](docs/IIKO_SETUP.md).

## Дальнейшее подключение iiko и настоящий запуск

Пошаговая инструкция — [docs/IIKO_SETUP.md](docs/IIKO_SETUP.md). GitHub Pages обслуживает статические файлы; секреты и серверный API iiko должны работать на отдельном backend. Переменные `VITE_*` попадают в публичную сборку, поэтому ключи iiko в них хранить нельзя.

Для промышленного запуска поверх проверенного локального сценария потребуются:

- Доступ к боевому iikoWeb, данные приложения и API-ключ предприятия, согласованные организация, меню, ценовая категория и касса. Секреты передаются через защищённое хранилище, не коммитятся в Git.
- Размещение backend с HTTPS, база данных, мониторинг и резервное копирование. Чтение меню, выбор поддерживаемых модификаторов, пересчёт цен, проверка стоп-листа и создание заказов уже работают локально; специальные схемы состава требуют отдельной поддержки и проверки.
- Серверная проверка зон доставки, минимальной суммы, тарифов и часов приёма заказов по действующим правилам ресторана.
- Настоящее подтверждение телефона, серверные сессии и проверка принадлежности заказов пользователю.
- Обновление этапов приготовления и доставки через защищённые webhooks. Подтверждение создания заказа и защита от повторной отправки уже реализованы локально.
- Интеграция бронирования с залами и занятостью столов, собственная ссылка регистрации карты и утверждённые правила лояльности.
- Если нужна онлайн-оплата — отдельный платёжный провайдер с серверной проверкой платежа.
- Действующие контакты и условия доставки, собственные фотографии, реквизиты и утверждённые документы по работе с данными гостей.

После подключения каждую функцию переключаем с демонстрационных данных на проверенный серверный сценарий. Отметки деморежима убираются только тогда, когда соответствующая интеграция действительно работает.
