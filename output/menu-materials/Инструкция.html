Шаг 1 Сопоставить блюда с номенклатурой

В демо можно создать учебные карточки. В действующем ресторане сначала ищем уже существующие блюда: сайт должен продавать те же позиции, по которым ресторан ведёт учёт.

  1. Открыть настольный iikoOffice: «Товары и склады → Номенклатура». Если используется веб-бэк-офис, открыть его справочник номенклатуры; не искать в нём дословно Windows-путь.
  2. Взять список 20 блюд из приложения к этому руководству. Для каждого найти совпадение по названию и уточнить, та ли это порция и рецептура.
  3. Отметить для себя «существующая карточка» или «новая карточка». Сохранить её артикул и внутреннее название. Длинное гостевое название позже задаётся во внешнем меню.
  4. Использовать найденную карточку повторно. Отдельная карточка нужна для действительно другого продукта или варианта учёта, а не просто для загрузки фотографии.
  5. Для отсутствующей позиции: «Номенклатура → Добавить → Новый элемент». Выбрать тип в соответствии с реальной работой: готовящееся блюдо и перепродаваемый готовый товар могут иметь разные типы.
  6. Указать внутреннее название, родительскую группу и уникальный артикул. Если формируете новые артикулы для учебного набора, удобно выбрать свободный числовой диапазон. Не копировать b1, soup1 и другие ID сайта как учётные идентификаторы.
  7. Сохранить карточку. Если использовалось «Действия → Копировать», перепроверить перенесённые настройки, рецепт и маршрутизацию.

Шаг 2 Проверить цену выход и приготовление

Ниже - поля, которые требуется проверить, а не готовая схема учёта. Для рабочего ресторана рецепт, списание и кухонную маршрутизацию подтверждают технолог, бухгалтер-калькулятор и администратор iiko.

  1. В основных свойствах выбрать фактические места продаж и тип места приготовления. Проверить связь с нужной кухней или баром, складом списания и сервисным принтером. Группа номенклатуры этих настроек не заменяет.
  2. Выяснить, откуда ресторан берёт продажную цену: из карточки или из приказа об изменении прейскуранта. Если применяются приказы, цену и места продаж проверять в них; изменение только карточки может не изменить продажу.
  3. Для приказов использовать «Прейскурант → Приказы об изменении прейскуранта», затем проверить действующий результат в прейскуранте товаров и услуг. Согласовать дату начала действия и ценовую категорию.
  4. На вкладке единиц измерения выбрать реальную единицу продажи и проверить вес порции. Для рабочего блюда выход должен соответствовать утверждённой технологической карте.
  5. В дополнительных сведениях проверить полное название и описание. Состав и аллергены взять из фактической рецептуры, а не автоматически считать достоверным текст макета сайта.
  6. Для готовящегося блюда проверить техкарту: ингредиенты, нормы, потери, выход и способ списания. Нельзя восстановить рецепт только по названию блюда и надписи «220 г».
  7. Если есть размеры, добавки, обязательный выбор соуса или гарнира, записать эти требования. Не снимать обязательность реального выбора ради подключения сайта.

Шаг 5 Обновить интеграцию и проверить демо

  1. В «Настройки Cloud API → Интеграции → Test API» выбрать подготовленное меню в поле «Внешнее меню» и сохранить. Подключённая точка должна соответствовать ресторану, из которого взяты блюда.
  2. Если создано новое внешнее меню, сообщить разработчику его название. На сервере нужно выбрать новый идентификатор меню и перезапустить API; текущий ID прежнего «Тест меню» сам не изменится.
  3. После правок основной номенклатуры обновить внешнее меню его кнопкой обновления, выбрать необходимые поля и подтвердить обновление. Это отдельный шаг: состав и описания внешнего меню не являются постоянно синхронизируемой копией справочника.
  4. На сайте проверить обновлённое меню. В локальном режиме используется адрес http://127.0.0.1:5173/#/delivery. Для немедленного перечитывания уже выбранного меню есть кнопка «Обновить меню и цены» на странице оформления. Обычная перезагрузка браузера может сохранить серверный кэш до 5 минут.
  5. Проверить все 7 категорий и 20 позиций: правильные названия, группы, цены, выход, описания, фотографии, наличие лишних тестовых блюд.
  6. Добавить одно блюдо в корзину, проверить цену и количество. Обновить страницу: состав должен сохраниться. Попробовать поиск и просмотр на телефоне.
  7. Оставить кассу онлайн. Оформить согласованный тестовый самовывоз с тестовыми контактами и комментарием «Проверка сайта». Кнопка действительно отправляет заказ в демо-iikoFront.
  8. Проверить обе стороны: сайт получил подтверждение, а выбранная касса показывает тот же состав, количество, сумму и самовывоз. Проверить нужную кухню или сервисный принтер.
  9. При неопределённом результате не создавать новый заказ с тем же составом. Использовать проверку состояния существующей заявки и сверить её с кассой.

Шаг 6 Подключить рабочий ресторан

В рабочем ресторане повторяем порядок действий, используя его реальные карточки, цены, кассу и меню. Демонстрационные идентификаторы и условные реквизиты не копируются как готовая боевая настройка.

  1. С управляющим утвердить ассортимент сайта, действующие цены, порции, описания, состав, аллергены и реальные фотографии. Согласовать упаковку и дополнительные платные позиции.
  2. С технологом или бухгалтером-калькулятором сопоставить карточки, проверить рецепты и списание. С администратором iiko проверить места продаж, карту приготовления и печать на нужной кухне.
  3. Подготовить рабочее внешнее меню и отдельное понятное имя интеграции сайта. Ограничить доступ нужной организацией и кассовой группой.
  4. Получить рабочий API-ключ. Разработчик выбирает реальные организацию, кассу и меню на сервере и проверяет чтение каталога. Секреты хранятся на сервере, не в документе и не в публичной сборке сайта.
  5. Выбрать, что запускается первым. Уже реализованный сценарий - самовывоз с наличными при получении. Для курьерской доставки отдельно нужны адреса, зоны, тарифы, сроки и проверка ограничений. Для онлайн-оплаты - отдельная интеграция.
  6. Разместить сервер сайта на постоянном хостинге с HTTPS и надёжным хранением заявок. Нынешняя локальная привязка к компьютеру не является готовым публичным размещением.
  7. Разработчик настраивает рабочий домен, путь запросов сайта к серверу, допустимые источники запросов, защиту оформления, резервное копирование и восстановление заявок. Публичный сайт на GitHub Pages сам по себе сервером заказов не станет.
  8. До открытия продаж доработать используемые модификаторы, расписания и сортировку. Определить, какие статусы гостю показываются после приёма кассой; полноценные стадии кухни и выдачи сейчас не подключены.
  9. Заменить примерные контакты, адрес, режим работы и документы сайта действующими данными ресторана. Решить вопросы подтверждения контактов, защиты от спама и доступа гостя к своему заказу.
  10. В согласованное время провести один сквозной тест в рабочем ресторане: сайт → нужная касса → нужная кухня. Проверить сумму, способ получения и оплаты; обработку тестового заказа завершить по процедуре ресторана.
  11. Открыть приём ограниченно, назначить сотрудника, который следит за первыми заказами. При сбое временно отключать оформление на сайте и показывать гостю понятное сообщение, сохраняя уже отправленные заявки.

Критерий допуска: не только успешная сборка сайта, но и подтверждённый заказ в нужном iikoFront, правильная кухонная маршрутизация и готовность сотрудников работать с этим источником.

Приложение Настройки подключения рабочего ресторана

Эта страница дополняет настройку меню. Порядок ниже позволяет подготовить локальную проверку. Для публичного запуска сервер и домен настраивает разработчик; запуск npm run dev не является размещением рабочего сайта.

  1. В iikoWeb рабочего ресторана создать интеграцию сайта, подключить нужную точку и разрешить доступ к его кассовой группе. Проверить доступность Cloud API и модуля приёма таких заказов с администратором iiko.
  2. В файле проекта server/.env указать данные приложения сайта и API-ключ именно рабочего ресторана. Если существующее приложение используется для этого сайта, отдельно проверить его действующие права и ключи. Секреты вводятся локально или в защищённые настройки хостинга.
  3. Сначала оставить IIKO_ORDERING_ENABLED=false. Из корня проекта запустить npm run iiko:check. По результату выбрать рабочую организацию и внешнее меню. ID кассовой группы можно скопировать в iikoWeb из столбца Id её настроек Cloud API.
  4. Заполнить идентификаторы из таблицы. Не переносить значения демо-организации «Мой ресторан», кассы «Дом» и прежнего «Тест меню» как настройки рабочего заведения.
НастройкаЧто в ней должно быть
IIKO_APP_ID; IIKO_CLIENT_SECRETДанные приложения сайта с портала разработчика. Не включать в архив материалов и не публиковать.
IIKO_API_KEYКлюч, которому разрешены нужные рабочие ресторан и касса.
IIKO_ORGANIZATION_IDID рабочей организации, полученный при проверке доступа.
IIKO_TERMINAL_GROUP_IDID кассовой группы, где должны приниматься заказы сайта.
IIKO_EXTERNAL_MENU_IDID подготовленного рабочего внешнего меню.
IIKO_PRICE_CATEGORY_IDТолько если для сайта действительно используется отдельная ценовая категория. Иначе пусто.
  1. Для локального интерфейса использовать .env.development.local с флагом VITE_CATALOG_SOURCE=iiko. API-ключ и Client Secret не должны находиться в переменных VITE_.
  2. После изменения server/.env остановить прежний API и запустить npm run api заново. Интерфейс запускается отдельно командой npm run dev. При изменении его файла настроек также перезапустить.
  3. После подготовки согласованного теста включить IIKO_ORDERING_ENABLED=true, перезапустить API и выполнить проверку из шага 5. Публичное оформление открывать только после выполнения чек-листа запуска.

Настройка VITE_CATALOG_SOURCE в development-файле действует только для локальной разработки. Для рабочей сборки и серверного адреса запросов нужна отдельная конфигурация развёртывания. Секреты при этом остаются на сервере.
